# 로그인 방식 제안

지금은 서버 없이 기기 안에만 암호화해서 저장하므로 로그인이 필요 없다. 사용자가 늘어 여러 기기 동기화나 계정이 필요해질 때의 권장 방향.

## 원칙
- **로그인과 암호화를 분리한다.** 로그인은 "누구의 데이터인지"만 확인하고, 일기 내용은 지금처럼 기기에서 암호화한 뒤 암호문만 서버로 보낸다 (종단간 암호화). 서버가 해킹되거나 운영자라도 일기를 읽을 수 없다.
- 지금의 데이터 키 구조(비밀번호로 감싼 키 + 복구 코드로 감싼 키)를 그대로 쓰면 서버에는 감싼 키와 암호문만 올라간다.

## 단계별 권장
1. **1단계: Google 계정으로 Drive 동기화 (자체 서버 없음)**
   Google 로그인 후 Drive의 앱 전용 폴더(appDataFolder)에 암호화 백업을 자동 저장. 서버 운영 비용과 개인정보 보관 부담이 없다. 로드맵에 이미 있는 항목.
2. **2단계: 자체 서비스가 필요해지면 소셜 로그인 + 관리형 인증**
   - 로그인 수단: **카카오, Google, Apple** (iOS 앱에서 소셜 로그인을 제공하면 Apple 로그인이 필수). 비밀번호를 직접 저장하지 않아도 된다.
   - 인증 서버: Supabase Auth 또는 Firebase Authentication 같은 관리형 서비스. 직접 구현하지 않는다.
   - 저장: 사용자별로 암호문(날짜, updatedAt, iv, ct)만 저장. 지금의 백업 파일 형식과 거의 같아 동기화 구현이 단순하다.
3. **이후: 패스키(Passkey)**
   지문/얼굴 인식으로 로그인. 앱 잠금 해제에도 생체 인증을 붙이면 매번 비밀번호를 입력하지 않아도 된다.

## 주의
- 일기 비밀번호(암호화용)와 로그인 계정은 별개다. 계정을 잃어도 복구 코드가 있으면 백업에서 복원할 수 있고, 일기 비밀번호를 잊으면 서버 운영자도 복구할 수 없다. 이 점을 가입 화면에서 분명히 안내해야 한다.
- 개인정보보호법상 수집 항목이 최소(이메일/소셜 ID)여야 하고, 일기 본문은 암호문이라 운영자가 열람할 수 없다는 점을 개인정보처리방침에 적는다.
